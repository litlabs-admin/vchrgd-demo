WHAT CHANGED

R1 Dependencies: Next.js 16.4.3, sharp 0.35.5, zod 4.6.7 and source-map-js 1.2.2
replace the affected versions. React and the Vercel OIDC integration stay on their
existing versions. The audit no longer reports the transitive Vercel/zod findings.
The existing eslint-config-next 16.3.6 and React hooks plugin 7.0.1 are retained
deliberately within their declared dependency range. Migrating that development
ruleset enabled seven new checks against unchanged UI; it is separate maintenance,
not a reason to modify checkout behaviour during this security change. The updated
runtime and the retained lint ruleset are both covered by final validation.

R2 Persistence: whole read/modify/write actions use PostgreSQL transactions and
transaction-scoped advisory locks. An AsyncLocalStorage context keeps nested JSON
operations on the same transaction connection. Locks cover absent keys and release
on rollback/disconnection. Payment state, audits, workflows, customer interactions,
admin access/attempts, product settings, saved views, installer/PO allocation,
work-order records and generic notification receipts use this protection.
The app_state table and JSON payload format stay compatible with existing data.
Local file/memory modes use process-local queues; production file writes and legacy
remote writes fail closed because those stores cannot provide these guarantees.
Production must use the existing Supabase/Postgres mode. Remote mode requires an
explicit transaction-protocol migration before it can be used for mutations.

R3 Balance collection: a durable per-workflow attempt is reserved BEFORE a provider
call. Simultaneous tabs/requests cannot create a second payable attempt. Subsequent
requests reuse the same URL; old pending attempts are adopted. Uncertain outcomes
remain blocked across clients/restarts for reconciliation, rather than issuing a
second charge. A method/amount change is blocked while an attempt exists.
No database transaction is held open during provider network calls.

R4 Frasers admin mutation: the old endpoint routes captures through the validated
capture helper with the recorded amount/currency and server-generated basket.
HTTP 202/PENDING does not mark an order completed or invoke fulfillment. Credits
and reversals through this endpoint return a clear instruction to use the confirmed
back-office Refunds workflow. Refunded/reversed payments cannot be recaptured.

R5 Refund state: verified card refunds may replace COMPLETED with REFUNDED. Refund
state is terminal against later payment callbacks. Reconciliation excludes refunded
sessions; late webhooks do not mark their customer interactions paid again. Old
customer card-return links redirect refunded customers to their order status.
Frasers reversal state also survives delayed authorisation/capture updates.

R6 Session revocation: administrator records carry an additive random session
version, regenerated by password/MFA/access changes. Signed sessions include that
version; validation checks it on every request. Disabling then re-enabling an
account never revives its old cookie. Bootstrap sessions bind to their configured
credentials. Password-login credential version is checked again when issuing the
cookie to reject a reset racing with sign-in. Google sign-in still uses the current
enabled account; the separate Workspace MFA policy acceptance gate remains.
Deploying this change requires administrators to sign in again once; customer
checkout/recovery/return tokens are unaffected.

R7 Generic Google Chat delivery: receipts are recorded only after confirmed 2xx
delivery. Definite HTTP rejection/missing configuration releases the reservation so
a retry can succeed. A lost/uncertain response retains its reservation and logs a
safe reconciliation message. The separate stage-alert transport is unchanged.

R8 Session API: lookups are awaited before fallback/serialization. A missing session
returns 404; a known UPR fallback returns its session; unauthenticated access is 401.
